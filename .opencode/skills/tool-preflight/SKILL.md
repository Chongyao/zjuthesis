# Tool Preflight Check (MANDATORY)

This skill must be invoked mentally by the agent before ANY `bash` or `task` tool call is generated.

## Context
In previous sessions, the agent's tool calls (specifically for `bash` and `task`) frequently failed with errors like:
`Invalid input: expected string, received undefined path: ["command"]`
or
`Invalid arguments: 'run_in_background' parameter is REQUIRED`.

This occurs because the underlying JSON payload generated by the agent is incomplete (missing required keys).

## The Checklist

Before outputting a tool call block for `bash` or `task`, you MUST verify the following schema compliance:

### For `bash` tool calls
- [ ] Are you passing the **`command`** argument? (e.g., `command="make safe"`)
- [ ] Is the `command` value a valid string?
- [ ] Are you passing the **`description`** argument? (e.g., `description="Compile thesis"`)

*Anti-pattern (will fail)*: `bash(description="Check status")`  -> MISSING `command`

### For `task` tool calls
- [ ] Are you passing the **`run_in_background`** argument? (e.g., `run_in_background=true`)
- [ ] Are you passing **`load_skills`**? (e.g., `load_skills=[]`)
- [ ] Are you passing exactly one of **`category`** OR **`subagent_type`**?
- [ ] Are you passing the **`prompt`** and **`description`**?

*Anti-pattern (will fail)*: `task(description="Do work", prompt="...")` -> MISSING `run_in_background` & `load_skills`

### For `edit` tool calls
- [ ] Is the `filePath` an absolute path?
- [ ] Are you passing `edits` as an array of objects?
- [ ] Does EACH edit object contain `op` (e.g., "replace", "append", "prepend")?
- [ ] Does EACH edit object contain `lines` (if replacing or inserting)?
- [ ] If replacing or deleting, are you using the EXACT `LINE#ID` format (e.g., `12#AB`) copied directly from a `read` output?

*Anti-pattern (will fail)*: Guessing `LINE#ID` tags instead of reading them first, or passing `lines` as a single string instead of an array.

### For `write` tool calls
- [ ] Is the `filePath` an absolute path?
- [ ] Is the `content` a valid string?
- [ ] Did you use `read` first if modifying an existing file? (Write OVERWRITES completely)

### For `background_output` tool calls
- [ ] Are you passing `task_id`?
- [ ] Are you waiting for the `<system-reminder>` completion notification before polling?
- [ ] Are you ending your response to allow the system to notify you, rather than polling in a loop?

## Troubleshooting & Recovery Protocol

If a tool call fails with validation errors (e.g., `Invalid input`, `received undefined`, `missing required parameter`):

1. **Acknowledge the specific error:** Do not guess. Look at the exact path/field mentioned in the error (e.g., `path: ["command"]`).
2. **Review your immediate previous response:** Did you actually include that field in your JSON payload? (Often, it was accidentally omitted when writing conversational text).
3. **Simplify the payload:** If the field *was* present but failed to parse, the issue is likely malformed JSON (e.g., unescaped quotes, problematic newlines in a bash command, or nested objects that broke the parser).
4. **Retry atomically:** Strip out conversational text. Issue ONLY the tool call with the most basic, strictly compliant JSON structure possible.

## Best Practices
1. **Never use shorthand**: The tool schema is strict. Do not assume the system will auto-fill required fields.
2. **Keep JSON payloads flat**: Avoid overly complex quotes or newlines in strings that might break the parser.
3. **One complex tool at a time**: If struggling with payload parsing, avoid parallelizing multiple complex `task` or `edit` calls in a single response.
